# 名医入企 · 北京大学国际医院企业健康服务平台

## 文档说明

### 编写目的

本文档描述“名医入企 · 北京大学国际医院企业健康服务平台”V1 的业务范围、角色权限、页面功能、字段规则、状态流转、异常处理与验收标准，作为技术开发、测试用例设计、产品验收和上线验收的共同依据。

文档以 2026-11-26 线上 V1 演示版本 `20261126-9` 的实际行为为基线。V1 演示端为纯前端 H5，正式上线版本采用 Vue 3 + 后端服务；本文档同时标注哪些能力属于演示实现、哪些必须由正式版后端承接。

| 读者 | 使用方式 |
| --- | --- |

| 产品与项目 | 对照 V1 需求范围验收；区分演示实现与正式上线必须承接的工程能力 |

### 需求范围

V1 覆盖机构端微信 H5 与院方工作台两条业务线，包含：机构白名单登录与企业资料、医院与定位推荐、专家库与筛选、时令主题、公开号源预约、提需、院方人工协调、提需转预约、预约状态流转、方案与附件、推送通知、号源配置、专家配置、时令主题配置、方案模版、医院与账号、机构账号白名单、展业海报和操作日志。

V1 不包含：在线支付、价格与报价展示、微信公众号授权登录、真实短信/邮件自动发送、真实后端库存与并发控制、合同与结算、发票、活动签到、评价与回访、院方主动取消预约入口。

## 产品概述

### 背景与目标

保险公司与企业需要把权威医疗资源带到客户身边，但专家资源分层复杂、医院履约范围不同、活动组织链路长。平台把“选专家、看主题、约时间、定方案、做提醒、完成归档”收敛到一条可追踪的线上链路，让机构可以自助发起，让医院运营可以按院管理，让超级管理员可以统一配置。

产品目标：

- 机构侧：在微信内无需下载、无需公众号授权即可完成登录、浏览、预约、确认与提需。
- 院方侧：按医院隔离资源与权限，接单后自动明确项目对接人，方案与推送一体化。
- 管理侧：专家、号源、时令主题、方案模版、展业海报均可配置，配置结果实时影响机构端展示与可约判断。
- 体验侧：移动端优先，操作局部刷新、保留浏览位置、支持安卓边缘返回，图片分层加载，避免卡顿。

### 用户角色

| 角色 | 使用端 | 核心诉求 | 关键权限 |
| --- | --- | --- | --- |
| 机构人员 | 微信 H5 | 快速找到可约专家、发起预约、确认方案、跟踪进度 | 浏览、预约、提需、取消/修改、查看本院资料 |
| 医院运营 | 院方工作台 | 接单、出方案、维护本院专家与号源、跟进需求 | 仅本院数据；接单后成为项目对接人 |
| 超级管理员 | 院方工作台 | 统筹全部医院、分配账号、维护配置、处理集团需求 | 全部医院与全部配置；机构白名单；操作日志 |

角色只有以上三种。此前的“项目负责人”不是独立角色，而是医院运营接单后自动形成的项目身份；同一账号可以在不同预约中担任不同项目的对接人。

### 核心业务流程

![图 1　总体业务流程](outputs/prd-shots/d1.png)

流程说明：

1. 机构人员登录后，系统按定位或手动城市推荐就近医院，默认展示该院可预约专家。
2. 机构选择服务类型、专家与公开可约日期，填写活动主题、参与人群、预计人数、活动地址与联系人。专家为必选项；没有合适专家或日期时走提需。
3. 提需由院方项目人员联系并人工匹配专家与履约日期，需求进入“已匹配”；院方匹配即临时占用该专家当日资源。机构基于匹配结果补充活动地址后确认生成预约，不再重新选择公开号源；预约生成后需求变为“已生成预约”，匹配安排锁定。
4. 医院运营在预约池接单，当前登录账号的姓名与手机号写入项目对接人快照，机构端开始显示具体对接人。
5. 医院运营填写方案并发送，系统生成个性化手机与邮件推送文案，预约进入“方案待确认”。
6. 机构确认方案或提出修改；确认后预约生效，院方执行并在结束后标记完成。
7. 公开号源与人工协调是两条互斥的库存分支：人工协调不扣减公开号源，但同一专家同一日期不能同时存在公开预约与人工协调预约；提交时还会重新校验提需是否被改期、关闭或重复转单。
8. 全程涉及专家属地、公开号源、人工协调日期、时令课题履约地、方案完整性与权限范围的多重校验。

## 账号、登录与权限

### 机构端登录

#### 前置条件

- 机构手机号已由超级管理员在“机构账号”中开通，且状态为启用。
- 当前浏览器可访问 H5；不依赖微信公众号授权，不获取微信头像、昵称或 OpenID。
- 演示环境验证码固定为 `888888`；正式版接入短信服务后改为真实验证码。

#### 登录流程

1. 机构人员点击首页右上角“机构登录”，进入手机号验证步骤。
2. 输入 11 位手机号、6 位验证码，勾选《企业健康服务预约须知》。
3. 系统校验手机号格式、验证码、协议勾选、白名单存在且启用。
4. 首次登录或资料不完整时进入“完善企业资料”步骤；资料完整时直接进入平台。
5. 登录成功后写入会话，关闭页面或重新打开仍保持登录；上次进入院方工作台时，下次打开优先回到院方工作台。

- 会话恢复时如资料仍不完整，正式版应再次拦截并引导补全；演示版仅在登录流程拦截。

#### 登录态与自动恢复

| 场景 | 期望行为 |
| --- | --- |
| 关闭页面后重新打开 | 保持机构登录态，直接进入上次所在端 |

### 院方登录

#### 前置条件

- 账号已由超级管理员创建并分配角色；医院运营必须绑定具体医院。
- 账号状态为启用；未分配、不存在或已停用的账号均不能进入。
- 从首页最下方“院方工作台”进入，或直接访问 `#/admin`。

#### 登录规则

- 使用账号 + 密码登录，演示密码为 `pkuih2026`。
- 超级管理员可查看全部医院；医院运营只能查看所属医院。
- 登录态持久保存；关闭后重新打开自动恢复，账号被停用则清除会话。
- 工作台顶部展示当前账号姓名、角色、所属医院与手机号；手机号可点击拨打。

### 时令主题

#### 主题结构

- 每家医院独立维护 12 个月主题；每月包含主题名称、时令说明、关注疾病、适合行业、主题图片、课题列表。
- 每个课题包含：科室/病种、讲座主题、主讲专家、课题履约地。
- 主讲专家必须是本院、启用、提供讲座服务的专家。
- 课题履约地按省市级联多选，支持“全国”；不同课题可以不同。
- 主题的可见范围不再使用月级“讲座覆盖城市”，而是由课题履约地汇总展示。

#### 时令主题详情

机构端主题详情展示：月份、主题名称、时令说明、关注疾病、适合行业、当前城市可约课题数、绑定专家数、课题履约范围、本月推荐讲座、绑定专家、预约按钮。

规则：

- 仅展示当前城市在课题履约地内的课题。
- 非本月主题只能浏览，不能预约；页面明确提示“往期主题仅供浏览，预约请选择本月主题”。
- 从预约流程进入主题详情时，课题选择结果回填预约；在当前城市不可约的课题置灰并阻止选择。
- 主题详情中的专家、课题、履约地必须与预约页使用同一套数据，不得出现详情可约、预约不可选。

#### 履约地语义

院方表格中的履约地写法需要兼容以下语义：

| 配置值示例 | 解释 |
| --- | --- |
| 北京 | 仅北京市 |
| 北京/京外 | 北京市 + 全国其他地区，按全国处理 |
| 山东 | 山东省 |
| 山东省内 | 山东省内城市 |
| 山东省内、省外 | 全国 |
| 山西 / 湖南 / 天津 / 深圳 | 对应省市 |
| 全国 | 不限城市 |

判定规则：配置值包含“全国”“京外”“省外”任一关键词时，视为全国可履约；否则按省份或城市名称归一化匹配。省、市名称比较时去除“省 / 市 / 自治区 / 特别行政区 / 地区 / 盟 / 自治州”等后缀。

### 省市数据与城市选择

- 全国省市数据包含 34 个省级行政区、380 个城市级选项。
- 所有需要选择履约地、活动城市、所在城市的地方，统一使用省市级联下拉，不允许自由文本输入城市。
- 省份切换后，城市列表必须立即刷新为该省城市；当前城市不在新省份时，自动选择该省第一个城市。
- 履约地支持多选城市；选择“全国”后不再叠加其他城市。

### 定位、城市与医院推荐

#### 定位流程

1. 首页加载后自动请求浏览器定位；用户拒绝或失败时不阻塞浏览。
2. 定位成功：计算与 9 家医院的距离，选择最近医院；首页医院下拉按距离升序排列。
3. 定位失败：按登录资料省市回退；无资料时提示手动选择城市。
4. 手动选择城市：写入本地配置，首页按该城市匹配医院；若无本地履约医院，推荐同省医院，仍无则推荐国际医院，并明确提示“本地暂无履约医院”。

#### 距离与排序

- 使用球面距离公式计算经纬度直线距离，展示“1 公里内 / 约 X.X 公里 / 约 X 公里”。
- 有定位时医院下拉严格按距离排序；无定位时当前医院优先，其次同省，再按名称排序。
- 医院切换后，首页统计、时令主题、就近专家、服务数量、专家库范围必须同步刷新。
- 机构资料中的省市不由用户填写；首页城市或定位变化时同步更新会话与企业资料。

#### 动态统计口径

| 指标 | 计算口径 | 切换医院后 |
| --- | --- | --- |
| 本院专家 | 当前医院 `active !== false` 的专家总数 | 立即按新医院重算 |

#### 医院切换交互

- 首页医院名称支持下拉切换，展示医院全称，不使用简称，避免用户无法分辨。

- 城市选择与医院切换并列展示，垂直居中对齐；按钮不得偏下或贴边。
- 医院名称在所有列表中加粗或使用强调色，与地址、科室等辅助信息区分。

#### 就近专家与服务入口

- 就近专家仅展示当前医院、覆盖当前城市、当前有剩余号源的专家。
- 排序：专业医生 → 主任专家 → 大咖医生；同层级按姓名排序。
- 点击专家卡进入专家详情；点击“全部专家”进入专家库并保持就近范围。
- 点击层级卡进入专家库，并预选对应层级。
- 点击服务卡进入专家库，并预选对应服务类型；服务卡数量必须与该服务可提供的本院专家数一致。

#### 首页验收要点

- 切换医院后三个统计数字均变化，且与本院数据一致。
- 时令主题卡只展示当前城市可约课题；无课题时不显示空卡或展示明确的空状态。
- 院方工作台入口只在页面最下方，不出现在“我的”。
- 页面底部无异常留白、悬浮文字或“已进入工作台”等错误提示。

- “就近医院”只包含当前医院专家，不再按专家履约地过滤（本院专家默认可服务本地）。
- “全部医院”必须过滤为“能服务当前城市”的专家；不能把全国所有专家无条件展示。
- “只看当地可约”只展示医院所在城市与当前城市一致的专家，避免异地医院被误认为本地资源。

### 发起预约

#### 前置条件

- 已登录机构账号，且企业资料完整。
- 公开号源预约：当前医院存在同时满足服务类型、活动城市、时令课题与公开号源条件的专家。
- 提需转预约：提需状态为“已匹配”，匹配专家仍有效且覆盖活动城市，院方匹配履约日期为今天或未来，提需尚未生成预约。
- 机构必须在预约确认页主动勾选确认；院方匹配结果不会自动生成预约单。

#### 流程

预约统一为两步，按来源分为两种模式：

1. 公开号源预约：服务类型、专家、期望日期、活动地点、活动需求、联系人 → 确认提交。
2. 提需转预约：院方匹配结果自动带入，服务类型、专家、履约日期锁定 → 补充活动地址、确认活动需求与联系人 → 确认提交。

#### 专家候选逻辑

公开号源预约：

1. 取当前医院的启用专家。
2. 过滤服务类型：专家服务列表包含当前服务。
3. 过滤时令：如果已选本月时令主题/课题，只保留主题绑定专家；选了具体课题则只保留该课题主讲专家。
4. 计算属地：普通服务按专家履约城市；时令按课题履约地。
5. 计算号源：未来日期中是否存在剩余号源。
6. 排序：可约优先 → 专业医生 → 主任 → 大咖 → 姓名。

不满足属地的专家仍可展示但标记“不含当前城市/不可履约”，按钮禁用；无号源标记“暂无号源”。两类不可选原因必须区分，不能统一显示“不可约”。

预约页专家候选列表必须在姓名旁展示梯队徽标：`大咖`、`主任`、`专业`，颜色沿用专家库层级标签。徽标用于快速识别资源层级，不得只靠头像、排序或职称文字暗示。

提需转预约：

1. 专家候选区只展示院方匹配专家，不展示同院其他专家。
2. 匹配专家必须属于目标医院、提供提需服务类型、日常履约地覆盖活动城市、状态为已显示。
3. 专家资料可点击查看，但不可改选；如匹配专家失效，阻止生成预约并提示联系项目人员重新匹配。
4. 提需匹配后、机构生成预约前，院方仍可更新匹配专家与履约日期；生成预约后锁定。

#### 日期逻辑

公开号源预约：

- 可约日期 = 专家号源中日期 ≥ 今天 + 专家提前期，且 `容量 - 公开号源已预约数 > 0`。
- 公开号源已预约数只统计 `manualArrangement = false` 且未取消的预约；人工协调预约不占公开号源。
- 已被院方匹配给提需、尚未转预约的专家日期，在提需取消/关闭前不进入公开可约日期；已生成人工协调预约的日期同样不再展示为公开可约。
- 已取消预约不占用号源。
- 同一天多个预约占用同一专家同一天号源。
- 日期列表只展示可约日期，不展示不可约日期；无日期时展示空状态与提需入口。
- 时令主题不改变专家的提前期，仍按专家提前期。

提需转预约：

- 日期取院方匹配的 `matchedDate`，在预约页以只读锁定卡展示，不展示公开号源日期选择器。
- 该日期允许不在公开号源中，但不得早于今天；过期匹配日期阻止生成预约并提示联系项目人员重新确认。
- 预约生成的 `coordinatedDate` 记录院方协调日期；院方后续在方案中改期时同步更新，并重新提交机构确认。
- 机构不得在预约页修改协调日期。

#### 时令主题选择

- 时令主题是可选条件，不选也可以自定义主题。
- 选择课题后，活动主题输入框锁定为课题名称，不允许修改；取消时令主题后恢复可编辑。
- 选择课题会收敛专家候选；如果当前已选专家不是该课题主讲，系统清空专家并提示。
- 切换活动城市后，如果所选课题不覆盖新城市，页面显示“当前城市不可预约”，并阻止下一步。
- 非本月主题不能带入预约。

#### 提交前校验顺序

1. 预约信息是否存在。
2. 服务类型是否选择。
3. 专家是否选择、是否有效、是否符合服务/医院/时令/属地/号源。
4. 日期是否选择；公开预约是否在可约日期内且有剩余号源；提需转预约是否为有效的未来协调日期。
5. 省市是否选择、详细地址是否填写。
6. 活动主题、参与人群、预计人数是否填写；人数是否为正整数。
7. 联系人姓名、联系电话是否有效。
8. 时令课题是否覆盖活动城市、是否属于当前专家。
9. 第二步是否勾选确认。

校验失败时：

- 顶部展示“还有 N 项需要补充”的汇总，可点击定位到字段。
- 字段标红并显示具体错误文案。
- 自动滚动到第一个问题并聚焦输入框。
- 同时弹出 Toast；不允许“点击下一步无反应”。

#### 第二步确认

展示活动主题、服务类型、日期、医院、专家、活动地点、主题履约地（如选了时令）、参与人群、预计人数、联系人、补充说明。

必须勾选“我已确认以上信息，并同意由院方项目组联系确认活动细节”后才能提交。

![图 20　预约确认](outputs/prd-shots/c17-booking-confirm.jpg)

#### 提交结果

- 生成预约编号，状态为“待接单”。
- 写入机构、医院、服务类型、专家、日期、活动地点、主题、人群、人数、联系人、备注、时令课题与履约地快照。
- 公开号源预约写入 `manualArrangement = false`。
- 提需转预约写入 `demandId`、`manualArrangement = true`、`coordinatedDate`，并回写提需 `convertedAppointmentId` 与转换时间。
- 成功转预约后需求状态写为 `converted`（已生成预约）；需求不能再次转预约、更新匹配或关闭。
- 不占用独立“锁单”记录；号源占用通过预约记录实时计算。
- 提交后进入预约详情，显示“院方接单后会显示项目对接人”。
- 提需转预约提交后同样进入待接单，院方仍需接单并确定项目对接人；不会因为提需已匹配而跳过接单。
- 若重复提交同一专家同一天导致公开号源不足，正式版必须由后端返回库存不足并提示重新选择；人工协调预约不参与公开库存扣减，但与公开预约、其他人工协调预约在同一专家同一日期互斥。
- 提交瞬间必须再次校验提需状态和匹配快照；院方在机构填写期间改期、改专家、关闭需求或需求已被转预约时，提交失败并提示返回提需详情。

| 已生成预约 | 机构基于匹配结果成功创建预约 | 显示“已生成预约”，提供“查看已转预约” | 匹配专家、医院、日期锁定；需求不可再匹配、关闭或取消，只能在预约单处理 |
| 已关闭 | 院方关闭 | 已关闭 | 仅查看 |
| 已取消 | 机构在未生成预约前取消 | 已取消 | 仅查看 |

规则：

- 机构可在“待联系 / 已联系 / 已匹配”且尚未生成预约时取消提需；取消后释放院方已匹配但未转预约的专家日期占用。
- “标记已匹配”必须先“已联系”，不允许从待联系直接跳到已匹配。
- 待联系时点击“标记已匹配”应提示“请先保存沟通记录并标记已联系”。
- 需求对接人由首次联系/匹配的院方账号自动写入。
- 院方匹配专家时必须校验：专家启用、服务类型匹配、履约地覆盖需求城市、目标医院匹配（指定医院需求）、专家当日无其他预约、该专家当日未被另一条已匹配提需占用。
- 院方匹配成功后，该专家当日日期立即从公开号源中临时占用；需求取消、关闭或匹配改期后释放。
- 机构确认生成预约时，系统重新读取提需最新状态；如果院方已改专家、改日期、改城市或需求已关闭/取消/已转预约，必须阻止提交并提示返回提需详情重新确认。

### 方案填写与提交

#### 页面结构

- 预约摘要：机构、联系人、期望主题、期望日期、活动地址、项目对接人、机构备注。

#### 方案字段

| 字段 | 必填 | 规则/说明 |
| --- | --- | --- |
| 活动主题 | 是 | 非空；可导入模版后修改 |
| 服务类型 | 是 | 讲座 / 健康咨询 / 1V1报告解读；保存时同步预约服务类型 |
| 出讲专家 | 是 | 必须是本院、启用、提供所选服务、覆盖活动城市、日期有号源的专家；保存时同步预约专家与层级 |
| 活动日期 | 是 | 不早于今天；必须在该专家可约日期内且有剩余号源；保存时同步预约日期 |
| 活动时长 | 固定 | 全天（1 天），不可修改 |
| 活动地点 | 只读 | 省份、城市、详细地址、场地名称来自机构；院方不可覆盖 |
| 课题大纲 | 否 | 多行文本 |
| 活动流程 | 否 | 多行文本 |
| 项目组成员 | 否 | 多行文本；默认可带入项目对接人 |
| 给机构的说明 | 否 | 多行文本；默认确认说明 |
| 方案附件 | 否 | PDF / PPT / PPTX，单文件 ≤ 20MB |
| 内部备注 | 否 | 仅院方可见，可编辑/查看切换 |

#### 保存校验

1. 预约存在且未完成/取消。
2. 已有项目对接人（先接单）。
3. 活动主题非空。
4. 活动日期非空且不早于今天。
5. 机构已填写详细地址；未填写时提示联系机构补充。
6. 出讲专家存在、本院、启用、服务匹配、属地匹配、日期号源充足。
7. 时令课题关联一致性：如果保留时令课题，则方案主题、专家、月份必须与课题一致；否则解除时令关联。
8. 附件类型与大小符合要求。

任一校验失败必须阻止保存并给出具体原因，不允许静默保存。

#### 保存后的系统行为

- 状态设为“方案待确认”，清空确认时间、机构反馈与修改申请，写 `planSentAt`。
- 方案写入预约，旧方案进入 `planHistory`。
- 同步更新预约日期、服务类型、专家、层级、时令月份/课题/履约地。
- 生成新的手机与邮件推送文案；旧推送记录失效。
- 若预约此前已确认，则必须重新由机构确认。
- 记录操作日志；Toast 提示“方案已提交，推送文案已生成”。

### 需求池

- 医院运营只看本院需求；超级管理员看全部医院需求与集团企康办需求。
- 集团企康办需求始终只对超级管理员可见，即使超级管理员当前选择了某家医院。
- 统计：待联系、已联系、已匹配（含待机构转预约）、已生成预约。
- 筛选：全部、待联系、已联系、已匹配、已生成预约、已取消、已关闭。

- 沟通记录可追加多条，记录内容、记录人、时间。
- “保存并标记已联系”：首次点击将待联系改为已联系，并写入当前账号为对接人；已有状态只保存沟通记录。
- “标记已匹配”：待联系时禁止，提示先标记已联系；已关闭禁止；成功后状态为已匹配。
- 匹配区选择专家与可履约日期；日期最早为明天、最晚一年内。允许选择公开号源为 0 或未到公开预约提前期的日期，这正是人工协调的适用场景。
- 匹配前必须校验专家服务类型、履约城市、专家所属医院与需求目标医院；同时拦截该专家当日已有预约、或已被其他已匹配需求占用的情况。

### 号源配置

#### 数据模型

- 号源按“专家 × 日期”存储，值为当日可预约数量，范围 0–30。
- 不区分上午/下午/时段；活动时长固定全天，为路程与准备预留时间。
- 同一专家同一天的所有服务类型共享同一份号源，不按服务拆分。
- 公开已预约数量 = 该专家该日期下所有非取消、`manualArrangement = false` 的预约数量。
- 剩余号源 = max(0, 当日号源数 - 公开已预约数)。
- 人工协调预约不扣减公开号源，但会在日历上标记“人工占用”；已匹配未转预约的提需标记“提需预留”。两类日期都不再进入机构端公开可约日期。
- 同一专家同一日期禁止同时存在公开预约与人工协调预约；院方匹配提需时即校验日期冲突。

4. 批量设置可约日。
5. 月份切换与日历。
6. 底部统一保存栏。

#### 批量设置

| 控件 | 规则 |
| --- | --- |
| 快捷范围 | 未来 7 / 14 / 30 天，仅调整起止日期，不立即保存 |
| 开始/结束日期 | 必填；开始不能晚于结束 |
| 每周可约日 | 至少选择一个星期；默认周一至周五 |
| 每日号源 | 0–30 的整数 |
| 设置给谁 | 当前专家 / 本院全部专家 |
| 加入待保存 | 写入草稿，不落库；日历显示“本次修改”标记 |

批量应用规则：

- 只处理所选星期内的日期。
- 早于“今天 + 该专家提前期”的日期自动跳过，并统计跳过数量。
- 目标值低于当日已预约数时，自动抬高到已预约数，并统计调整数量。
- 批量设置只调整公开号源，不覆盖“人工占用 / 提需预留”标记；这些日期即使配置了数量，也不会对机构端开放。
- 应用后自动定位到开始日期所在月份。
- 批量应用不直接保存，必须点击底部“统一保存”。

- 点击日历日期打开当日号源弹窗。

- 当日号源不得低于已预约数；低于时禁用保存并显示警告。
- 过去日期、早于提前期的日期不可配置。
- “加入草稿”后返回日历，仍需统一保存。

#### 统一保存

- 底部实时显示“N 处修改未保存”。

## 关键业务规则

### 可预约判定的统一管线

所有入口（首页、专家库、专家详情、预约页、院方方案页）必须使用同一套判定，禁止各自实现导致结果不一致。

```text
可预约(专家, 服务, 城市, 日期) =
  专家启用
  且 专家属于当前医院
  且 专家服务包含该服务
  且 时令条件满足（若选了课题：课题主讲=专家 且 课题履约地覆盖城市）
  且 日常履约地覆盖城市（若未选时令）
  且 日期 >= 今天 + 专家提前期
  且 当日不存在人工协调预约
  且 当日不存在已匹配但尚未转预约的提需预留
  且 当日号源 - 已预约数 > 0
```

专家“当前可约” = 存在至少一个满足上述条件的日期。

### 筛选结果一致性

- 筛选计数、空状态、专家卡片必须来自同一个结果集。
- 服务类型计数 = 当前范围与可约状态下，提供该服务的专家数。
- 切换服务类型后，专家列表只能出现提供该服务的专家。
- 开启月份时令后，只展示讲座，且只展示本月有课题、课题覆盖当前城市、专家匹配的专家。
- 不允许出现“筛选显示 1 位，进入后展示全部专家”或“筛选后无结果但计数不为 0”。
- 任何筛选操作只局部刷新，不重建整页，不丢失滚动位置。

### 号源计算公式

```text
容量 C(e,d)      = 专家 e 在日期 d 的号源数（0–30）
已约 B(e,d)      = 专家 e、日期 d 下所有非取消且非人工协调的公开预约数
剩余 R(e,d)      = max(0, C(e,d) - B(e,d))
可约日期集合 D(e) = { d | d >= today + lead(e)
                     且 R(e,d) > 0
                     且 d 无人工协调预约
                     且 d 无已匹配提需预留 }
```

规则：

- 预约占用号源，取消释放号源；已完成仍占用历史，不回补。
- 号源按专家共享，不按服务类型拆分。
- 人工协调预约独立于公开号源，不写入公开号源扣减，但其日期对公开预约封闭；公开预约的日期也不可再被人工匹配，保证同一专家同日只有一条资源安排。
- 单日容量上限 30；保存时不得低于已预约数。
- 批量设置低于已预约数时自动抬高到已预约数。
- 早于提前期的日期不可配置、不可预约；已存在的历史配置保留但不参与可约计算。
- 正式版必须在数据库层使用唯一约束或行锁，避免并发超卖。

### 属地判定

| 场景 | 使用的属地 | 说明 |
| --- | --- | --- |
| 普通讲座、健康咨询、1V1报告解读 | 专家履约城市 | 由专家配置的 `coverageCities` 决定 |
| 时令主题 | 课题履约地 | 由每个课题的 `coverageCities` 决定 |
| “全部医院”专家库 | 当前城市 | 专家日常履约地必须覆盖当前城市 |
| “只看当地可约” | 当前城市对应医院 | 医院所在城市必须等于当前城市 |
| 时令主题可见性 | 当前城市 | 课题履约地不覆盖当前城市则不展示 |
| 时令主题预约 | 活动城市 | 进入预约后按活动城市再次校验 |

关键要求：时令主题的属地与专家日常属地是两套数据，不能相互覆盖。修改专家履约城市不应自动修改课题履约地；修改课题履约地也不应改变专家日常服务范围。

| 当前状态 | 操作 | 操作人 | 条件 | 下一状态 | 副作用 |

- 院方更新匹配安排时，如果机构已打开旧预约页，提交时必须因快照不一致被拦截。
- 同一提需重复提交必须被状态与 `demandId` 唯一性同时拦截。

- 接单人 = 当前登录的院方账号。

### 分配与可见范围

```text
机构人员可见：本人手机号下的预约、提需、本人资料
医院运营可见：hospitalId = 本人所属医院 的预约、需求、专家、号源、主题、模版、海报
超级管理员可见：全部医院；集团企康办需求；机构白名单；院方账号；操作日志
```

集团企康办需求的路由优先级最高：即使超级管理员当前选择了某家医院，集团需求仍在需求池中可见；医院运营永远不可见。

### 推送复制状态判定

```text
复制状态有效 =
  存在复制记录
  且 复制时间 >= max(方案更新时间, 方案发送时间)
```

- 方案每次保存都会更新 `plan.updatedAt` 与 `planSentAt`，因此旧复制记录自动失效。
- 预约列表出现“推送待复制”标签的条件：存在方案、状态属于待确认/待修改/已确认、推送复制记录无效。
- 邮件复制仅记录操作日志，不参与手机推送复制状态判定；不要求发送回执或失败重试。

### 前后端分层与接口边界

V1 前端已经将基础设施与页面业务拆开，正式接后端不需要重新定义请求格式。

| 文件 | 职责 | 约束 |
| --- | --- | --- |
| assets/config.js | 运行时环境配置 | 唯一配置入口；维护 apiMode、apiBaseUrl、authMode、超时与客户端版本 |
| assets/api.js | 数据源、HTTP、持久化、会话 | 页面只能通过 `PkuihApi` 访问基础设施 |
| assets/app.js | 页面状态、业务规则、渲染与交互 | 不得直接读写 localStorage，不得直接请求业务静态数据 |
| docs/API-CONTRACT-V1.md | 前后端接口契约 | REST 路径、响应包、字段、状态机、权限、错误码、并发与幂等规则 |
| docs/CODE-REVIEW-V1.md | V1 代码审查记录 | 记录已修复风险、剩余生产级后端承接项与架构规则 |

运行模式：

| 模式 | 配置 | 数据来源 | 用途 |
| --- | --- | --- | --- |
| local | `apiMode: "local"` | 静态 JSON + 浏览器本地持久化 | 线上演示、业务评审 |
| api | `apiMode: "api"` | `/api/v1/bootstrap` + 后端资源接口 | 正式联调与生产 |

统一契约：

- 响应包为 `{ code, message, data, requestId }`，`code = 0` 表示成功。
- 请求头携带 `X-Request-Id`、`X-Client-Version`；写操作携带 `Idempotency-Key`。
- 登录态默认使用 `HttpOnly; Secure; SameSite=Lax` Cookie，不把长期 token 写入 localStorage。
- `assets/api.js` 提供超时、401/403 处理、网络错误归一化、端点模板与路径参数编码。
- 基础数据加载统一走 `PkuihApi.data.bootstrap()`；页面不得自行拼接静态文件地址。
- 医院、专家、号源、预约、提需、主题、附件、海报、通知的端点和字段以 `docs/API-CONTRACT-V1.md` 为准。

工程门禁：

- `npm test` 检查 JavaScript 语法、页面存储直连、静态数据直连、API 端点完整性、HTTP 契约能力与构建可重复性。
- `tests/architecture.test.cjs` 防止后续页面绕过 API 层。
- GitHub Actions 在 push 和 pull request 时执行同一质量门禁。

## 交互与非功能需求

### 移动端与微信环境

- 目标视口 390×844，兼容 320px 宽度；页面不得横向溢出。
- 直接通过微信内置浏览器打开 H5，不依赖公众号授权、不调用微信登录、不要求 App 安装。
- 适配 iOS 安全区与底部手势条；底部导航、弹层底部按钮不得被遮挡。
- 微信内 PDF 预览受内核限制时，提供“微信内打开”或下载兜底；PPT/PPTX 直接下载。
- 支持 `tel:` 拨号；手机号在详情中显示为可点击链接。
- 安卓微信边缘滑动返回：按“当前弹层 → 上一级弹层 → 工作台/客户端 → 退出”顺序逐层返回，不能直接退出业务页面。
- 弹层支持下滑关闭、点击遮罩关闭、点击关闭按钮关闭；不能只能点某一个按钮才能退出。

### 登录态与数据隔离

- 机构与院方会话分别持久化；上次进入院方工作台时优先恢复院方。
- 机构预约、提需按手机号隔离；院方数据按医院隔离。
- 退出登录清除对应会话与内存状态；不得残留上一账号数据。
- 正式版冷启动必须重新校验账号启用状态与白名单状态。

### 滚动位置保持

- 列表进入详情、详情返回列表、筛选切换、弹层关闭后必须恢复原滚动位置。
- 禁止使用会强制回到顶部的整页重渲染；筛选与切换使用局部刷新。
- 浏览器 `history.scrollRestoration` 设为 manual，由应用统一保存与恢复。
- 预约页、专家库、我的预约、需求池、号源页、专家管理、时令配置均需覆盖。

### 弹层与返回栈

- 弹层打开时锁定背景滚动，关闭后恢复原位置。
- 多层弹层（预约 → 专家详情 → 主题详情）逐层关闭，返回目标必须是上一层，不得跳到其他菜单。
- 登录弹层从任意页面触发时，登录成功后回到触发页与滚动位置；不能因登录弹层被遮挡而“点击无反应”。
- 安卓返回与浏览器返回使用同一套 history 层级，不允许一层返回直接退出。

### 加载性能

- 首屏只加载必要资源；医院主图使用 960px 宽版本并设置 `fetchpriority=high`。
- 专家列表使用卡片缩略图，详情图仅在打开详情时加载；全部 `loading=lazy`。
- 海报列表只加载缩略图，打开预览再加载完整图。
- 脚本与样式使用压缩版本，静态数据带版本号；版本变更时统一更新 `DATA_VERSION` 与 HTML 引用。
- 筛选、切换层级、选择日期/专家不得触发整页刷新；交互反馈应在 100ms 内出现。
- 大量图片上传前压缩；专家图 540×680，海报最长边 1920。
- 目标：4G 网络首屏可交互时间 ≤ 3 秒；已加载页面内筛选响应 ≤ 200ms；无长任务导致的明显卡顿。

### 空状态、错误与提示

| 场景 | 展示 |
| --- | --- |
| 无匹配专家 | 说明原因 + 切换范围/清除筛选 + 发起提需 |
| 无号源 | 明确“暂无号源”，提供其他专家/日期或提需 |
| 无预约/提需 | 空状态插画与引导文案 |

| 操作成功 | Toast 明确结果；重要操作刷新对应局部区域 |
| 权限不足 | 明确提示“仅超级管理员/仅本院”，不静默失败 |
| 未登录点击受限操作 | 弹出登录层，登录后回到原操作与滚动位置 |

### 视觉与可用性

- 品牌色使用北京大学国际医院深蓝体系；橙色仅作强调，不大面积使用。
- 文字与背景对比度满足 WCAG AA：正文 ≥ 4.5:1，大字号 ≥ 3:1。
- 禁止浅灰字叠浅蓝底、白字叠浅色图等不可读组合；手机号、医院名称、状态必须清晰。
- 医院名称在列表中加粗或使用强调色；状态标签颜色与语义一致。
- 关键按钮触控区域 ≥ 44×44px；底部按钮固定时不得遮挡内容。
- 图标与文字基线对齐；卡片、表单、筛选栏左右边距统一，不得贴屏幕边缘。
- 中文文案使用统一术语：院方工作台、项目对接人、方案待确认、推送通知、履约地、号源、提需。

### 安全与隐私

- 不展示价格、合同、结算信息。
- 手机号仅在必要页面展示，并支持拨打；正式版列表默认脱敏，详情按权限展示。
- 机构只能访问本人数据；院方只能访问本院数据；附件下载必须鉴权。
- 前端不得信任角色与医院参数；所有接口服务端二次校验。
- 操作日志记录关键写操作，至少保留 180 天；演示版本地 300 条。
- 上传文件限制类型与大小，服务端需病毒扫描与内容审核。

### 兼容性

- iOS Safari、微信 iOS 内核、Android Chrome、微信 Android 内核。
- 320px、375px、390px、414px、430px 宽度下无横向滚动、无文字截断。
- 不支持定位时全部功能可手动完成；不依赖剪贴板时提供手动复制兜底。
- 不支持 `tel:` 的桌面环境降级为展示号码。

## V1 工程边界与正式上线前承接项

以下为 V1 演示版受纯前端形态限制、必须由正式版后端或正式运营能力承接的事项。业务范围仍属于 V1；技术与测试需按正式上线要求纳入接口、数据与验收设计：

| 编号 | 限制 | 影响 | 建议 |
| --- | --- | --- | --- |
| GAP-01 | 机构会话冷启动未重新校验白名单状态 | 账号停用后旧会话可能仍可浏览 | 正式版每次启动调用 `/session` 校验账号状态 |
| GAP-02 | 无院方取消预约入口 | 院方无法主动取消，只能线下沟通后由机构取消 | 增加院方取消申请、原因、审批与双方通知 |
| GAP-03 | 无后端库存与并发锁 | 多端同时预约可能超卖 | 号源事务扣减、唯一约束、失败回滚 |
| GAP-04 | 邮件复制不记录独立状态 | 无法判断邮件是否已实际发送 | 不属于 V1 范围；如需审计，只持久化邮件复制记录 |
| GAP-05 | 无真实短信/邮件网关 | 需院方复制后人工发送 | 产品明确不接入发送网关，不需要模板审核、回执或失败重试 |
| GAP-06 | PPT/PPTX 不能微信内预览 | 只能下载后用 WPS/PowerPoint 打开 | 服务端转 PDF 预览或接入 Office 预览 |
| GAP-07 | 未接入微信 JS-SDK | 无法自定义分享卡片、无法获取微信身份 | 如运营需要，绑定公众号后补充分享与授权 |
| GAP-08 | 医院仅支持电话编辑 | 不能新增医院、修改地址/经纬度 | 后台增加医院管理与地图选点 |
| GAP-11 | 无活动签到、评价、回访 | 履约闭环止于完成 | 增加签到码、满意度、回访任务 |
| GAP-12 | 海报存 localStorage | 大图易触达容量上限 | 对象存储 + CDN + 素材审核 |
| GAP-13 | 号源不按服务类型拆分 | 讲座/咨询/1V1 共享同一天容量 | 如业务需要，改为 `(expert,date,service)` 维度 |
| GAP-14 | 无自动站内信/订阅消息 | 方案更新依赖院方复制推送 | 如需增强，只做站内通知；不要求短信自动发送 |
| GAP-15 | 客户资料变更不回溯历史预约快照 | 历史推送/联系人仍为旧值 | 明确快照策略，必要时提供“同步最新资料” |
| GAP-16 | 提需“已匹配”日期没有自动过期释放 | 机构长期不确认时会持续占用该专家日期 | 增加匹配有效期（如 72 小时）与到期提醒，超时自动释放或由院方手动释放 |

正式上线前承接顺序：

1. P0：后端鉴权、号源事务、状态机接口化、附件鉴权、推送复制记录持久化。
2. P1：院方取消、站内通知、医院管理、提需预留过期释放、活动地点变更留痕。
3. P2：微信分享、签到评价、数据看板、导出报表、海报渠道追踪。
