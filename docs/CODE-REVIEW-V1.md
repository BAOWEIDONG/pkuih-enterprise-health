# 名医入企平台 V1 代码审查记录

审查日期：2026-11-26

审查范围：H5 演示前端、数据持久化、登录态、预约/提需状态流转、上传与构建流程

当前基线：`20261126-9`

## 1. 本次已完成的工程整改

### 1.1 统一服务层

- 新增 `assets/config.js`，集中维护 API 模式、服务地址、超时和客户端版本。
- 新增 `assets/api.js`，统一提供基础数据、持久化、HTTP 客户端、端点清单和会话 token。
- 页面代码不再直接访问 `localStorage`。
- 页面启动不再直接请求 `assets/data/*.json`，统一调用 `PkuihApi.data.bootstrap()`。
- 正式接入后端时，页面交互不需要改；替换数据源与实体接口实现即可。

### 1.2 HTTP 客户端规范

- 统一超时控制与中止逻辑。
- 统一注入 `Authorization`、`X-Request-Id`、`X-Client-Version`。
- 默认使用服务端 `HttpOnly Cookie` 登录态，不把长期 token 暴露给页面代码。
- 统一解析 `{ code, message, data, requestId }` 响应包。
- 统一处理 401、403、网络错误、超时和业务错误。
- 不把 token、短信密钥或后端地址散落在业务代码中。

### 1.3 数据访问边界

- 业务页面只使用 `readJSON`、`writeJSON`、`removeJSON` 三个持久化入口。
- 持久化实现集中在 API 层，替换 IndexedDB、离线缓存或远程仓储时不需要逐页修改。
- 基础数据加载、版本参数和空数据校验集中在 API 层。

### 1.4 工程校验

- 新增 `package.json`，固定 `esbuild@0.28.2`。
- 新增 `tests/architecture.test.cjs`，阻止业务页面重新直连存储或静态数据。
- 新增 GitHub Actions 质量门禁，检查语法、构建可重复性和架构约束。
- 构建命令统一为 `npm run build`，验收命令统一为 `npm test`。

## 2. 逻辑审查结论

已确认并修复的风险：

| 风险 | 处理 |
|---|---|
| 提需匹配日期无公开号源，但机构仍应能转预约 | 使用人工协调号源，不计入公开容量 |
| 提需重复转换可能生成多个预约 | 事务内检查 `demandId`、状态和既有预约 |
| 院方匹配后修改日期/专家，机构仍按旧信息提交 | 提交前校验提需快照，过期即拦截 |
| 提需预留日期可能被公开预约占用 | 匹配时预留日期，公开预约排除预留日 |
| 人工协调预约可能与公开预约冲突 | 同专家同日统一冲突校验 |
| 号源批量保存与日历显示不一致 | 保存后刷新草稿与日历，统一缓存失效 |
| 号源容量可能低于已预约数量 | 保存前与后端双重校验 |
| 预约状态可被跨状态操作 | 前端按钮约束 + 接口状态机双重校验 |
| 普通预约与提需转换重复下单 | 幂等键 + 服务端事务 + 前端提交锁 |

## 3. 仍需后端承接的生产级事项

以下事项不能靠静态 H5 解决，正式上线必须由后端实现。

### P0 安全与权限

1. 登录验证码必须由服务端生成、限流、一次性消费。
2. 所有角色和医院归属必须由服务端从 token 解析，不能信任前端字段。
3. 医院运营、超级管理员、机构账号的数据范围必须在服务端过滤。
4. 密码、验证码、短信供应商密钥不得出现在前端包或浏览器存储中。
5. 附件必须私有存储、短时签名、病毒扫描和内容审核。

### P0 库存与并发

1. 号源扣减、提需预留、人工协调预约必须在数据库事务中完成。
2. 同一专家同一日期必须使用行锁、唯一约束或条件更新，防止超卖。
3. 创建预约必须支持幂等键；重复请求返回同一结果。
4. 批量号源保存必须整批成功或整批失败，并带版本号防止覆盖他人修改。

### P1 状态与审计

1. 预约、提需状态机由服务端强制执行。
2. 状态变更、方案确认、取消、推送复制都要写审计日志。
3. 短信/邮件由服务端队列发送，记录供应商回执、失败重试和退订状态。
4. PDF/PPT 在线预览使用短时签名链接，不暴露长期存储地址。

### P1 数据一致性

1. 专家、医院、时令主题变更应有版本号或更新时间。
2. 时令课题履约城市和专家日常履约城市分别存储、分别校验。
3. 医院停用后，其专家、号源和历史预约应保留归档，不允许物理删除。
4. 机构资料变更后，历史预约保存提交时快照，避免历史记录被新资料覆盖。

## 4. 前端架构规则

当前演示仍是原生 JavaScript 单页，原因是需要在不引入构建迁移风险的前提下稳定业务闭环。代码审查后确定以下边界：

1. 页面渲染、业务状态和 DOM 事件暂时保留在 `assets/app.js`。
2. 基础数据、HTTP、持久化、会话 token 必须经过 `assets/api.js`。
3. `assets/config.js` 是唯一运行时环境配置入口。
4. 新页面不得直接访问 `localStorage`、`fetch` 业务数据或硬编码 API 地址。
5. 正式 Vue 3 工程迁移时，`API-CONTRACT-V1.md` 作为接口层验收依据，页面组件不得重新发明请求格式。

建议 Vue 3 目录映射：

```text
src/
  api/            # 复用本契约，拆分为 auth/hospital/expert/appointment/demand
  stores/         # Pinia：session、location、booking、admin
  composables/    # 滚动恢复、定位、筛选、上传、状态机
  components/     # 专家卡、医院切换、日期号源、方案、弹窗
  views/          # 首页、专家库、预约、记录、工作台
  utils/          # 日期、金额禁用规则、城市级联、权限判断
```

## 5. 交互与性能审查

- 页面切换和筛选采用局部刷新，不重建整页。
- 弹层关闭、返回、筛选切换保留浏览位置。
- 列表图片分层加载，详情图按需加载。
- 号源、专家、主题筛选共用同一结果集，避免“筛选显示与详情不一致”。
- 表单提交前统一展示缺失字段，避免用户逐项寻找。
- 所有用户输入进入模板前必须经过 `esc()`；新增渲染函数需继续遵守。
- 轮询或远程刷新上线后必须做差量更新，不得整页刷新。
