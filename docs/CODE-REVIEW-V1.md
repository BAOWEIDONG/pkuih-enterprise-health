# 名医入企平台 V1 代码审查与交付就绪度

审查日期：2026-11-26
审查基线：`3ee7b3e`
审查范围：Vue 3 生产入口、原有 H5 业务层、Spring Boot API、数据与权限边界、构建和回归链路

## 1. 结论

| 交付层级 | 状态 | 结论 |
|---|---|---|
| 静态 H5 演示 | 可用 | 可直接用于业务评审、微信内置浏览器演示和客户验收 |
| 前后端联调 | 部分可用 | 登录、专家查询、号源、预约、提需主链路已有后端实现和前端客户端封装，但业务页面尚未全面切换到 API |
| 正式生产接管 | 未就绪 | 缺少完整业务接口、前端业务 API 客户端、生产级验证码、数据库迁移、文件与消息服务、审计和端到端联调 |

因此不能只把 `apiMode` 改为 `"api"` 就宣称全系统已可上线。当前代码适合“演示 + 联调基础”，不适合直接替代生产系统。

## 2. 技术栈变更影响

当前生产入口已经是 Vue 3 + Vant + Vite，但业务页面尚未拆成 Vue 组件。

- `web/src/components/LegacyHost.vue` 只创建原有 `#app`、`#overlay-root`、`#toast` 挂载点。
- Vue 外壳继续加载 `assets/config.js`、`assets/api.js`、`assets/app.js`。
- 页面渲染、状态管理、筛选、预约、滚动恢复等仍位于 `assets/app.js`。
- `assets/styles.css` 没有因为 Vue 接入被替换或覆盖。

| 范围 | 是否变化 | 说明 |
|---|---|---|
| 构建与运行外壳 | 是 | 已改为 Vue 3 + Vant + Vite 构建 |
| 现有视觉样式 | 否 | 继续使用原 CSS 和原 DOM 结构 |
| 业务流程与交互 | 否 | 仍由原有 `assets/app.js` 执行 |
| 本地演示数据 | 否 | 仍使用浏览器 `localStorage` / `IndexedDB` |
| Spring Boot API | 独立新增 | 已实现核心履约闭环，但尚未全面接入页面 |
| 页面组件化 | 否 | 目前是 Vue 外壳兼容运行，不是 Vue 业务组件迁移 |

当前视觉回归证明“Vue 入口与原始入口渲染一致”，证明范围是外壳没有造成像素偏移；它不是历史版本 golden snapshot，也不能替代专家详情、预约详情和工作台等深层页面的交互回归。

## 3. 后端已实现能力

Spring Boot 已实现并通过集成测试的核心能力：

- CSRF、机构验证码登录、院方账号密码登录、Session 恢复与退出。
- 医院、专家、时令主题、课题匹配和省市数据的 Bootstrap。
- 专家公开查询和院方专家新增、编辑。
- 按专家和日期查询号源，院方批量保存号源。
- 机构创建预约、查询列表与详情。
- 院方接单、提交方案、记录内部备注、完成归档。
- 机构确认方案、申请修改、取消预约、更新活动地点。
- 提需创建、查询、联系、匹配和关闭。
- 集团企康办提需只允许超级管理员处理。
- 医院运营的数据范围限制在本院。
- 号源保存不得低于已预约数量。
- 提需匹配日期预留、提需重复转换拦截和预约冲突校验。

集成测试覆盖机构登录、查询号源、下单、院方接单、提交方案、机构确认、提需分流、提需预留和号源容量下限。

## 4. 尚未达到生产接管的部分

### P0：会直接阻塞上线

1. 前端业务页面仍默认使用本地存储，没有把专家维护、时令配置、号源、预约、提需、海报和附件操作全部切换到后端。
2. 契约已声明但后端尚未实现：时令主题配置、方案模板、展业海报、文件上传与签名地址、推送通知记录。
3. 验证码仍是固定演示码 `888888`，没有真实发送、一次性消费、过期、限频和错误次数控制。
4. 文件仍保存在浏览器 `IndexedDB`；生产环境需要私有对象存储、20MB 限制、类型校验、病毒扫描、短时签名 URL 和权限隔离。

### P1：上线前必须加固

1. 没有操作审计日志，无法追踪接单、方案修改、取消、号源调整、内部备注和推送状态。
2. 短信、邮件、推送发送记录、供应商回执、失败重试和退订状态尚未接入。
3. 专家、医院、时令主题等管理接口仍使用部分 `Map<String,Object>` 入参，字段级校验和前端类型契约不够严格。

### P2：可维护性

1. `assets/app.js` 约 1.65 万行，仍是单文件业务运行层；后续应由 Vue 3 组件、Composition API 和 Pinia 逐步接管，同时保留现有 CSS 与视觉回归门禁。
2. 现有视觉回归只覆盖首页、专家、预约、我的四个主 Tab，尚未覆盖专家详情、时令详情、预约流程、预约详情、院方登录和全部工作台页面。
3. 后端部分 Service 存在未使用的依赖和重复校验，应在正式开发时清理。

## 5. 当前工程优点

- 前后端分层清楚，API 契约、统一错误包、CSRF、Session 和角色校验已有基础。
- 医院运营的数据范围在服务端过滤，不依赖前端隐藏按钮。
- 号源库存使用数据库行锁，提需预留和人工协调预约已有冲突校验。
- 关键状态流转有服务端状态机校验，取消规则按专家层级区分提前期。
- 停用账号的旧会话会即时失效；幂等键会校验请求指纹；预约状态使用乐观锁；号源批量保存会校验聚合版本。
- Flyway 迁移、`ddl-auto: validate` 与迁移结构测试已接入。
- 前端有架构门禁、语法检查、压缩产物可重复构建和视觉回归。
- GitHub Actions 的 `spring-api`、`legacy-h5`、`vue-web` 三组检查均通过。

## 6. 开箱使用说明

### 可直接使用

静态 H5 演示：

```bash
npm test
python3 -m http.server 8080
```

后端本地启动：

```bash
cd server
mvn spring-boot:run
```

### 不能直接使用

不能把以下配置当成生产上线开关：

```bash
VITE_API_MODE=api
VITE_API_BASE_URL=/api/v1
```

在补齐第 4 节 P0/P1 项并完成页面到 API 的端到端联调前，该配置只能用于局部接口联调，不能用于正式接管。

## 7. 上线前验收门槛

1. 所有业务页面只通过 API 读写，禁止再写浏览器本地业务数据。
2. 补齐后端缺失接口与前端 API 客户端，并以 OpenAPI 或契约测试锁定字段。
3. 接入真实验证码、审计日志和异常告警。
4. 完成 PostgreSQL 预发迁移和回滚演练。
5. 文件、短信、邮件、推送全部接入真实服务并保留发送回执。
6. 补齐越权访问、并发接单和高并发号源场景测试。
7. 扩展视觉与交互回归到全部关键页面，并完成微信 Android/iOS 真机验收。

## 8. 审查结论

V1 演示代码可以继续用于业务评审和联调准备，UI 不会因为 Vue 3 接入发生改变；但当前架构仍是“Vue 外壳 + 原有业务运行层”。在完成业务 API 接管、生产级鉴权与库存并发、数据库迁移、文件与消息服务之前，不应把当前版本定义为可直接生产使用的前后端成品。
